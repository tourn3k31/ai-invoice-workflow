# Software Requirements Specification (SRS)

## AI Invoice Workflow

**Version:** 1.0  
**Status:** Portfolio MVP  
**Primary Stack:** React, TypeScript, ASP.NET Core 8, Entity Framework Core, SQLite, Azure App Service, Azure Static Web Apps

---

## 1. Purpose

The AI Invoice Workflow application is a portfolio-grade invoice-processing system that demonstrates how a business can upload invoices, extract structured data, validate financial information, detect possible duplicates, review exceptions, approve or reject invoices, and measure processing outcomes.

The current MVP uses a deterministic text extractor rather than a production OCR or AI document-extraction service. The architecture is designed so the extractor can later be replaced with Azure AI Document Intelligence, Azure OpenAI, AWS Textract, Google Document AI, or another production document-processing service.

---

## 2. Business Need

Many organizations receive invoices through email, document portals, and shared folders. Employees commonly spend time:

- Reading invoice fields
- Copying information into internal systems
- Verifying totals
- Checking for duplicates
- Identifying missing information
- Routing invoices for approval
- Tracking processing volume and value

The application reduces manual effort by automating extraction and validation while retaining human review for questionable invoices.

## 5. Assumptions and Constraints

- The MVP accepts `.txt` files only.
- Input files must use the supported field format.
- File size is limited to 5 MB.
- SQLite storage may reset after Azure App Service redeployment or restart.
- The Azure frontend and backend are deployed separately.
- CORS must allow the deployed frontend origin.
- The current extractor is deterministic and does not perform OCR.
- The current confidence score is generated by the demo extractor.
- The current deployment uses Azure free-tier services where available.

## 6. Functional Requirements

### FR-001 — Upload Invoice

The system shall allow a user to select and upload one invoice file.

**Acceptance criteria:**

- The upload control accepts a file.
- The backend receives the file.
- Empty files are rejected.
- Files larger than 5 MB are rejected.
- Unsupported file types are rejected.
- Successful uploads create an invoice record.

### FR-002 — Extract Invoice Header Fields

The system shall extract:

- Vendor name
- Invoice number
- Invoice date
- Due date
- Purchase-order number
- Subtotal
- Tax
- Total
- Confidence score

**Acceptance criteria:**

- Extracted values appear in the invoice detail view.
- Missing required fields generate validation findings.

### FR-003 — Extract Line Items

The system shall extract invoice line items containing:

- Description
- Quantity
- Unit price
- Calculated line total

**Acceptance criteria:**

- Each valid item appears in the line-item table.
- Line totals equal quantity multiplied by unit price.

### FR-004 — Validate Invoice Totals

The system shall compare the stated subtotal, tax, total, and line-item calculations.

**Acceptance criteria:**

- The calculated line-item sum is compared with the stated subtotal.
- Subtotal plus tax is compared with the stated total.
- A mismatch creates an error-level validation finding.
- An invoice with an error-level finding requires review.

### FR-005 — Detect Missing Required Fields

The system shall identify required fields that are missing or blank.

Required fields include:

- Vendor name
- Invoice number
- Invoice date
- Total

**Acceptance criteria:**

- Missing fields create validation findings.
- The invoice status becomes `NeedsReview`.

### FR-006 — Detect Duplicate Invoices

The system shall flag an invoice as a possible duplicate when a non-rejected invoice already exists with the same vendor name and invoice number.

**Acceptance criteria:**

- Duplicate detection runs during upload.
- The invoice detail view displays the duplicate result.
- Duplicate status is included in metrics.

### FR-007 — Assign Invoice Status

The system shall support:

- `Processing`
- `NeedsReview`
- `Approved`
- `Rejected`

**Acceptance criteria:**

- A successfully validated invoice may be approved automatically in the current MVP.
- An invoice with an error-level finding or low confidence becomes `NeedsReview`.
- A user may manually approve an eligible invoice.
- A user may manually reject an invoice.

### FR-008 — Approve Invoice

The system shall allow a user to approve an invoice without unresolved error-level findings.

**Acceptance criteria:**

- Approval changes the status to `Approved`.
- Approval updates the modification timestamp.
- Approval is blocked when error-level findings exist.
- The approved value metric updates.

### FR-009 — Reject Invoice

The system shall allow a user to reject an invoice.

**Acceptance criteria:**

- Rejection changes the status to `Rejected`.
- Rejection updates the modification timestamp.
- Rejected invoices are excluded from duplicate matching.

### FR-010 — Display Invoice List

The frontend shall show uploaded invoices in a selectable list.

Each list item shall display:

- Vendor
- Invoice number
- Total
- Status

### FR-011 — Display Invoice Details

The frontend shall display:

- Source file name
- Vendor
- Invoice status
- Invoice fields
- Confidence
- Duplicate indicator
- Line items
- Totals
- Validation findings
- Approval and rejection controls

### FR-012 — Display Metrics

The application shall show:

- Total processed
- Approved count
- Needs-review count
- Approval rate
- Approved value

The API shall additionally expose:

- Duplicate count
- Average confidence

### FR-013 — Retrieve Invoices Through API

The backend shall expose endpoints to retrieve:

- All invoices
- One invoice by identifier

### FR-014 — Update Invoice

The backend shall expose an endpoint that updates invoice values and line items.

**Acceptance criteria:**

- Existing line items are replaced.
- Validation runs again.
- The invoice returns to `NeedsReview`.
- The update timestamp changes.

### FR-015 — Error Feedback

The application shall inform the user when:

- The backend cannot be reached
- A file cannot be uploaded
- Validation blocks approval
- Processing succeeds
- An operation fails

## 7. API Requirements

### GET `/api/invoices`

Returns all invoices with line items and validation findings.

### GET `/api/invoices/{id}`

Returns one invoice by GUID.

### POST `/api/invoices/upload`

Accepts a multipart invoice file and returns the created invoice.

### PUT `/api/invoices/{id}`

Updates extracted fields and line items.

### POST `/api/invoices/{id}/approve`

Approves an invoice when no error-level validation findings remain.

### POST `/api/invoices/{id}/reject`

Rejects an invoice.

### GET `/api/metrics`

Returns processing metrics.

## 9. Validation Rules

### VR-001 — Required Vendor

Vendor name must not be blank.

### VR-002 — Required Invoice Number

Invoice number must not be blank.

### VR-003 — Required Invoice Date

Invoice date must be present and valid.

### VR-004 — Positive Total

Invoice total must be greater than or equal to zero.

### VR-005 — Line-Item Subtotal

The sum of all line totals must match the stated subtotal within the configured currency tolerance.

### VR-006 — Invoice Total

Subtotal plus tax must match the stated total within the configured currency tolerance.

### VR-007 — Confidence Threshold

Confidence below 80% shall require review.

### VR-008 — Duplicate Detection

Matching vendor and invoice number shall create a duplicate indicator unless the existing invoice is rejected.

---

## 10. Nonfunctional Requirements

### NFR-001 — Usability

A new user should be able to upload and inspect an invoice without training.

### NFR-002 — Performance

For the MVP, a supported text invoice should normally process within five seconds under light load.

### NFR-003 — Availability

The hosted demonstration should be accessible through Azure when the free-tier services are running.

### NFR-004 — Reliability

The API shall return structured error responses for expected validation failures.

### NFR-005 — Maintainability

The extraction implementation shall be accessed through `IInvoiceExtractor` so it can be replaced without changing endpoint behavior.

### NFR-006 — Security

- Secrets shall not be committed to Git.
- API credentials shall be stored in environment settings or GitHub secrets.
- The backend shall allow only configured CORS origins.
- Uploaded filenames shall be sanitized before storage.
- File type and size shall be validated.

### NFR-007 — Portability

The frontend and backend shall run locally and in Azure.

### NFR-008 — Accessibility

Interactive controls should provide visible hover, focus, active, and disabled states.

### NFR-009 — Observability

The backend should support application logging and Azure App Service log streaming.

### NFR-010 — Data Durability

SQLite is acceptable for the demonstration only. A production version shall use durable managed storage such as Azure SQL.

## 13. Test Scenarios

### TS-001 — Valid Invoice

Upload a complete invoice with correct totals.

**Expected:** The invoice processes successfully and has no validation findings.

### TS-002 — Incorrect Total

Upload an invoice where subtotal plus tax does not equal total.

**Expected:** `TOTAL_MISMATCH` appears and the invoice requires review.

### TS-003 — Missing Invoice Number

Upload an invoice without an invoice number.

**Expected:** A required-field validation finding appears and the invoice requires review.

### TS-004 — Duplicate Invoice

Upload the same vendor and invoice number twice.

**Expected:** The second invoice is marked as a duplicate.

### TS-005 — Empty File

Upload an empty file.

**Expected:** The API rejects it with a bad-request response.

### TS-006 — Unsupported File

Upload a file other than `.txt`.

**Expected:** The API rejects it.

### TS-007 — Approve Invalid Invoice

Attempt to approve an invoice with an unresolved error-level finding.

**Expected:** Approval is blocked.

### TS-008 — Reject Invoice

Reject an existing invoice.

**Expected:** Status changes to `Rejected`.

### TS-009 — Backend Offline

Load the frontend while the API is unavailable.

**Expected:** The frontend displays a backend-connection message.

### TS-010 — Cloud Deployment

Open the Azure Static Web App and call the Azure App Service API.

**Expected:** CORS permits the request and metrics load.

## 14. Acceptance Criteria

The MVP is accepted when:

- The frontend and backend deploy successfully.
- A user can upload a valid test invoice.
- Header fields and line items are displayed.
- Correct totals pass validation.
- Incorrect totals produce a validation error.
- Missing fields produce a validation finding.
- Duplicate invoices are flagged.
- Approval and rejection endpoints work.
- Metrics update after processing.
- The frontend can call the Azure backend.
- The repository includes setup and architecture documentation.

---

## 15. Known Limitations

- The application is not yet using a true AI extraction service.
- Only structured text invoices are supported.
- SQLite data may reset after Azure redeployment or restart.
- There is no authentication.
- There is no audit trail identifying who approved an invoice.
- There is no editable review form in the current frontend.
- There is no automated evaluation dataset dashboard.
- The confidence score is not produced by a trained model.
- The MVP should not be used for actual financial processing.
